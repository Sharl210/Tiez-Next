# v0.5.42 — 正文不再被截断

## 这次修的是什么

你反馈的那行 `CUSTOMER_LABEL = MOLY.NR17.R2.... [HTML Truncated]`，是**读列表时后端主动把正文剪短**造成的。一共四处，这次全部拆掉了。

| 位置 | 之前的坏行为 |
|---|---|
| 后端读取列表 | 正文超过 2000 字就切掉，尾部拼上 `... [Truncated for speed]` |
| 后端读取列表 | HTML 超过 5000 字就切掉，尾部拼上 `... [HTML Truncated]` |
| 后端推送更新事件 | 同一条正文再被剪一次（粘贴后刷新那一瞬间） |
| 前端列表渲染 | 表格超过 3 行就删掉后面的行，塞进一行 `... content truncated for preview ...` |

## 为什么这次必须连根拔掉，而不是再调大阈值

因为这四处不只是"显示少一点"，它会**真的把数据弄丢**：

列表下发的正文，同时也是**正文编辑器的初始值**。你对一条长条目点一次「编辑 → 保存」（哪怕一个字都没改），编辑器就会把那份被剪短的正文原样写回数据库。库里的完整原文就此永久变成残缺版，没有任何提示，也撤不回来。

所以真正危险的不是"看不全"，而是"被悄悄存坏"。

## 改完之后

- 库里的正文是什么，界面就拿什么；富文本 HTML、纯文本、以及富文本转纯文本**都不再丢内容**。
- 列表里看到的高度仍然被限制（CSS 的 `max-height` 加渐隐遮罩），那是**画面**的边界，不再是**数据**的边界。
- 拿不准的地方一律倒向"保真"：宁可让列表多占一点高度，也不剪正文。

## 顺手做掉的加固

- 原本在两个列表命令、一个标签命令里各写了一遍的"整理正文"逻辑，收敛成同一个函数，避免以后再改只改一处。
- 补了 **11 条回归测试**（后端 4 条 + 前端 7 条）盯着这件事：
  - 400 行的长正文读回来必须逐字相同；
  - 长 HTML 必须逐字相同；
  - 表格 9 行必须全在 DOM 里；
  - **最关键的**：编辑器初值是长正文、直接保存，送回去的正文长度必须不变（就是上面那条回写链）。
- 这些测试做过反向验证：把截断逻辑塞回去，它们会立刻报红，不是摆设。

## 你需要注意的两件事

1. **已经被存坏的条目不会自己长回来。** 完整的原文只在"你曾经编辑并保存过"的那种条目上丢掉了。其余条目库里一直是完整的，这次改动后就能看到全文。
2. **有一处截断我故意留着**：调用 AI（改写/翻译/社交嘴替）时，送给模型的正文有 10000 字上限。这是模型上下文长度的硬约束，去掉会让请求直接失败，属于"功能限制"而不是"数据丢失"。如果你的条目经常超过 1 万字需要 AI 处理，告诉我，我改成明确提示而不是静默截取。

## 顺带修掉的一个隐藏问题：更新检查其实一直是坏的

排查时发现，`latest.json`（应用内"检查更新"要读的那个文件）**从 v0.5.32 之后就没再发布过**，中间 9 个版本都没有。也就是说：

```
https://github.com/Sharl210/Tiez-Next/releases/latest/download/latest.json
→ HTTP 404
```

你点"检查更新"永远不会提示有新版本——不是"已经是最新版"，而是**根本查不到**。

这次把 `latest.json` 重新补齐并随安装包一起发布。补上之后端点能正常解析，后续版本也会继续带着它发；否则这个洞会一直存在。

（这一条和截断无关，是顺手发现的独立缺陷，单独说明以免混淆。）

## 验证方式

- 前端 343 条测试通过（含 7 条新的保真回归），TypeScript 类型检查零错误。
