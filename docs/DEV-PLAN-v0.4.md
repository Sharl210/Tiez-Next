# Tiez-Next v0.4 开发计划

配套文档：`docs/REQUIREMENTS-v0.4.md`（需求规格）。本计划给出**批次划分、依赖顺序、风险、验收方式**。

- 计划版本：v0.4-draft
- 当前基线：`94e611f`（v0.3.4）
- 目标：完成 R1–R11

---

## 总览

| 批次 | 内容 | 需求 | 风险 | 依赖 |
|---|---|---|---|---|
| **B1** | 数据层奠基（schema 11：`note` 列 + 备份所需清单确认） | R6 数据侧 | 低 | 无 |
| **B2** | 内容管线缺陷修复 | R5.1、R5.2 | **高**（需先取证） | 无 |
| **B3** | 多显示器窗口行为 | R1 | **高**（三现象联动） | 无 |
| **B4** | 标签系统增强 | R2、R3、R4、R11 | 中 | R6 数据侧 |
| **B5** | 主页面编辑 + 备注显示 + 粘贴计入历史 | R6、R7、R10 | 中 | R6、R4 |

| **B8** | 整体回归与验收 | 全部 | — | 全部 |

**排序理由**：
1. B1 先做——`note` 列是 R6/R10 的数据基础，且**必须在 B6 定格式前完成**，否则备份格式要改两次。
2. B2、B3 是**缺陷修复**，独立于新功能，优先解决用户日常痛点。
3. B4/B5 是 UI 增强，依赖 B1 的列。
4. B6 备份格式一旦发布就是长期契约（R8.4），必须等 schema 稳定后再定。
5. B7 MCP 复用 B6 的导出能力，放最后。

## B2 内容管线缺陷修复（R5）

### B2.0 先取证（**前置，不可跳过**）
用户报告的是**现象**，修复前必须拿到真实数据：
1. 让用户复现「复制链接」后，检查该条记录的 `content` / `preview` / `html_content` / `content_type` 实际值 → **判断原始 URL 是否还在**。
   - 若 URL 在 `html_content` 的 `href` 中 → 修复偏向「解析还原 + 改变 `content` 落库策略」
   - 若已彻底丢失 → 必须改采集逻辑
2. 确认「粘贴为纯文本」走哪个函数，为何也取不到 URL。
3. 图片被吞：确认是否为 `mod.rs:544-571` 的哈希构成问题（文本与图片混入同一 hasher）+ `cached_image` 复用导致哈希相同。

### B2.1 图片被吞
- 修正 `mod.rs:544-571`：**文本哈希与图片哈希分离**，避免不同图片因缓存复用而哈希碰撞
- 检查 `cached_image` 的生命周期：确认每次剪贴板事件后缓存被正确失效
- 补充单测：连续不同图片 → 全部入库；同一图片连续 → 去重生效

### B2.2 链接变标题
- 优先保 URL；标题作为附加信息（可入 `note` 或 `preview`）而非取代 `content`
- 修正「粘贴为纯文本」使其输出 URL 而非标题

### 风险
- **高**：去重逻辑牵一发动全身，改动可能影响富文本/Office 场景（代码注释明确提到 WPS/Office 多次触发剪贴板事件依赖该窗口）
- 缓解：改动后必须回归「Office/WPS 复制富文本不产生重复条目」

## B3 多显示器窗口行为（R1）

### B3.0 前置确认（阻塞性）
勘察报告提出三个需用户确认的输入：
1. 副屏相对主屏的**方位**与是否负坐标（验证「交界即边缘」假设）
2. 唤起方式（Alt+C / Win+V / 鼠标中键 / 托盘）
3. 当前 DB 中 `app.follow_mouse`、`app.edge_docking` 的实际值

### B3.1 修复「跨屏跳变」
- `window_manager.rs:267-335`（else 支路）：**去掉"发现不同屏就 remap 搬窗"**，改为窗口位置由**唤起屏**决定
- 新增「唤起屏」记录（`global_state.rs`）：在窗口显示时记录所在显示器，后续显示以此为准
- `window_manager.rs:191-266`（was_docked 支路）：同样以唤起屏为基准
- `window_manager.rs:123-190`（follow_mouse 支路）：保留跟随鼠标能力，但**默认值改为 false**，并补前端开关（`GeneralSettingsGroup.tsx`）+ 修正前后端默认值不一致（`database.rs` 补 `app.follow_mouse` 默认行；`useSettingsPostInit.ts:319` 对齐）

### B3.2 修复「自动置顶」
- `setup.rs:907-936`：**移除自动 `WINDOW_PINNED.store(true)`**，只保留贴边停靠的视觉/位置行为（若保留）
- 或将自动置顶限定为「**用户主动拖拽窗口到边缘**」才触发，排除「程序自动摆位恰好落在边缘」
- **解耦 5px 耦合**：`window_manager.rs:169-171` 的 clamp 值与 `setup.rs:801` 的 `threshold` 不得相同

### B3.3 修复「异屏点击隐藏」
- `hooks/mod.rs:446-457`：点击在**另一块显示器**上时**不隐藏**窗口
  - 实现：判断点击点是否落在「窗口当前所在显示器」之外的显示器 → 是则跳过隐藏
- `setup.rs:1338-1390 handle_blur`：失焦隐藏逻辑同样按显示器判断，异屏失焦不隐藏

### 验收
见 `REQUIREMENTS-v0.4.md` R1 验收条件 1–5（含"显式图钉仍可用"）。

### 风险
- **高**：三现象联动（pin 后走"保持可见"分支掩盖了隐藏问题），改一处可能露出另一处
- 缓解：改完后**必须**用真机双屏验证；无法在 Linux 验证（Windows 专用 API），需用户配合验收

## B6 备份导出 / 导入恢复（R8）

### B6.1 导出
- 新增 Rust 依赖 `zip`（**需验证 cargo-xwin 交叉编译可过**）
- 新增命令 `export_backup(dest_path)`：
  1. 对数据库做一致性快照（WAL 模式下需 `VACUUM INTO` 或 checkpoint）
  2. 打包 `clipboard.db` / `attachments/` / `emoji_favorites/` / `datapath.txt` / 自定义背景
  3. 写入 `manifest.json`（含 `format_version` / `schema_version` / 计数 / 每个文件的 sha256）
- 前端：设置页新增入口 + 文件保存对话框

### B6.2 导入
- 新增命令 `import_backup(zip_path)`：
  1. **校验** `format_version`：高于支持范围 → 拒绝并提示升级（前向兼容边界）
  2. **自动备份当前数据**到 `<data>.backup-<ts>`
  3. 解压到临时目录 → 校验每个文件 sha256 与 manifest 一致
  4. 校验通过才替换现有数据
  5. 失败 → **回滚**到第 2 步的备份
  6. 数据库被占用 → 采用「标记待恢复 + 重启后替换」策略（复用既有 `datapath.txt` 式重定向经验）
- 前端：二次确认（明确"现有数据将被替换"）+ 结果反馈（含备份路径）

### B6.3 双向兼容规则落地
- 建立 `format_version` 常量与升级函数骨架（即使当前只有版本 1）
- 在 `docs/` 记录兼容性约定，作为后续版本的强制规则
- 补兼容性测试：导入 v1 包 → 成功；伪造 v99 包 → 安全拒绝

### B6.4 完全恢复验收（关键）
按 R8.2 的 8 项逐项比对，**用真实数据**做导出→清空→导入→逐项校验的端到端测试。

### 风险
- **高**：破坏性操作（覆盖现有数据）
- 新增 `zip` 依赖的**交叉编译风险**需先验证
- 缓解：严格遵循「先备份→校验→替换→失败回滚」

## B7 MCP 服务（R9）

### B7.1 架构选择（待决策）
两个候选：
- **(i) 应用内 HTTP MCP server**：复用 `axum`（已在依赖），直接调 repository，随应用启动
- **(ii) 独立 sidecar 二进制**：直接读写同一 SQLite

**建议 (i)**：`axum` 已就绪，可复用全部业务逻辑与事务；无需处理双进程并发写同一 DB 的 WAL 竞争。

### B7.2 能力映射
将 R9 所需操作映射到已有命令 / repository 方法。**前置**：确认业务逻辑是否已抽到 service/repository 层（若是，直接复用；若否，先将命令内的逻辑下沉）。

### B7.3 安全
- 仅绑定 `127.0.0.1`
- 写操作需鉴权 token（`uuid` 生成，存数据目录，UI 可查看/重置）
- 提供**只读模式**开关
- 复用既有 `privacy`/`sensitive`/`ENCRYPT_PREFIX` 机制，敏感条目不因 MCP 而暴露

### 验收
R9 验收条件 1–6

### 风险
- 中高：MCP 可写数据；需防误操作
- 缓解：默认只读、显式开启写、token 鉴权、所有写操作记日志
