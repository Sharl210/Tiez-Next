# 维护责任传递清单

> **这份文档是给未来接手这个项目的人（或未来的你自己）看的。**
>
> 它记录的是：**过去某个时间点做的一个决定，会在之后持续影响维护工作**。
> 这类影响不会出现在功能文档里，也不会在编译时报错——它只会在某天有人"顺手改一下"的时候
> 静静地把东西弄坏，或者让人反复困惑"这里为什么这么写"。
>
> 所以每一条都回答四个问题：
> **做了什么 · 为什么这么做 · 之后的人需要注意什么 · 什么时候这条可以撤销**。
>
> **本文档不依赖任何外部资料。** 你不需要读过需求文档、提交记录或任何人的笔记，
> 只读这一份就能理解每一项的来龙去脉。

## 怎么用这份文档

- **改动相关代码之前**：在下面的目录里搜一下你要碰的文件或概念，看有没有相关条目。
- **觉得某段代码"很奇怪、像是写错了"时**：先查这里。很可能它是**故意的**，理由就写在本条目里。
- **要"清理旧代码"之前**：特别注意标题带「刻意保留」的条目——那些旧名字删掉会**损坏用户已有的数据**。
- **你自己做了一个会产生长期负担的决定时**：**加一条进来**，见文末《如何新增条目》。

**本文档与 `README.md` 的「维护约定」是两份不同的记录，别混淆：**

| 文档 | 记录什么 | 读者 |
|---|---|---|
| `README.md` | **产品是什么样**（功能、与上游的差异、每个版本改了什么） | 用户、潜在贡献者 |
| `维护文档.md`（仓库根） | **决策的时间与替代关系**（按时间追加、只增不改、带索引与 SUPERSEDES 链） | 追溯决策链的人 |
| **本文档** | **维护时要注意什么**（哪些地方碰了会出事、旧代码为什么不能删） | 改代码的人 |

## 一、上游分叉带来的长期负担

### M-01｜自定义安装器模板会与上游分叉

**做了什么**
安装器现在使用**仓库内的自定义模板**，目的是让覆盖升级时**默认"直接覆盖"**，
而不是默认"先卸载再安装"。

| 文件 | 作用 | 大小 |
|---|---|---|
| `src-tauri/nsis/installer.nsi` | 安装器模板本体（与上游唯一的差异见下表） | 32,340 字节 / 971 行 |
| `src-tauri/nsis/gen-reinstall-probe.py` | 生成下面那个行为探针的脚本 | — |
| `src-tauri/nsis/reinstall-default-selftest.nsi` | 探针（**自动生成，不要手改**） | 6,301 字节 |

打包配置里用 `bundle.windows.nsis.template` 指向模板（`tauri.conf.json`，只加了这一行）。

**为什么这么做**
打包工具自带的模板在"升级已有安装"时会弹一个页面（提示这是升级、不是重装），
**默认选中"安装前先卸载"**。用户手快点了下一步就会先跑卸载。虽然实测卸载器并不删用户数据
（数据不在安装目录里，见 M-04），但默认行为本身会让人担心"卸载会不会顺手删掉我的东西"。
两个单选按钮的顺序与默认态写在模板内部，**只能靠替换模板来改**（官方的
`customLanguageFiles` 只能改文案，改不了默认选中）。

**提示页保留**：本次只改默认选中项，页面本身照旧弹出——用户仍然能看到"这是在升级"的说明，
只是默认项从"先卸载"变成了"直接覆盖"。

**与上游模板的精确差异**

这份模板不是"从生成产物里抄一份"，而是**取上游模板原文**
（上游模板**逐字内嵌**在 `node_modules/@tauri-apps/cli-linux-x64-gnu/cli.linux-x64-gnu.node` 里，
从 `Unicode true` 的偏移开始，到 `Function CreateOrUpdateDesktopShortcut ... FunctionEnd` 结束），
因此差异只有**本次改动本身**：**1 处、1 个函数**。

- 函数：`PageReinstall`（第 253 行起，页面创建函数）
- 位置：两个单选按钮创建完之后、`nsDialogs::Show` 之前（第 265–291 行）
- 改动：默认选中的判定多了一层"升级/降级"判断；`${NSD_SetFocus}` 的目标同步跟随

改动前（上游）——**首次进入永远勾第一个按钮**：

```nsis
${If} $ReinstallPageCheck <> 2
  SendMessage $R2 ${BM_SETCHECK} ${BST_CHECKED} 0   ; $R2 = "安装前卸载"
${Else}
  SendMessage $R3 ${BM_SETCHECK} ${BST_CHECKED} 0
${EndIf}
${NSD_SetFocus} $R2
```

改动后（本项目）——升级/降级勾第二个按钮，同版本保持原样：

```nsis
${If} $ReinstallPageCheck <> 2
  ${If} $R0 <> 0
    SendMessage $R3 ${BM_SETCHECK} ${BST_CHECKED} 0 ; $R3 = "请勿卸载"
  ${Else}
    SendMessage $R2 ${BM_SETCHECK} ${BST_CHECKED} 0
  ${EndIf}
${Else}
  SendMessage $R3 ${BM_SETCHECK} ${BST_CHECKED} 0
${EndIf}
${If} $R0 <> 0
  ${NSD_SetFocus} $R3
${Else}
  ${NSD_SetFocus} $R2
${EndIf}
```

`$R0` 的含义由模板自己定义：`0` = 已装同版本、`1` = 升级、`-1` = 降级。
所以 `$R0 <> 0` 就是"升级或降级"，同版本时**行为与上游完全一致**。
模板里用注释标出了这段的起止（`--- Tiez-Next 本地改动` / `--- Tiez-Next 本地改动结束`），
只改这两行注释之间的内容，就不会误伤上游代码。

**改动了多少（编译实测）**

| 指标 | 上游模板 | 本项目模板 |
|---|---|---|
| 安装器指令数 | 1875 条 / 52,500 字节 | 1885 条 / 52,780 字节 |
| 字符串 | 572 | 573 |
| 页面 / 节 | 6 页、3 节 | **6 页、3 节（不变）** |
| 卸载器 | 785 条指令 | **785 条指令（不变）** |

**之后的人需要注意什么**
- 模板是**上游维护的**。我们复制出来的这一天起，上游对模板的修复**不会自动进来**。
- 打包工具升级后，**必须**把这个新模板与官方模板对比一次，把无关的修复合并进来。
  否则会慢慢积累出"我们这份缺了官方后来修的问题"。
- **同步时不要拿本文档当依据去手改上游模板**——正确做法是反过来：
  以上游模板为基线，重新贴一次本文档里那段改动。因为上游模板会持续变化，
  而这段改动是稳定的。
- **改动要尽可能小**：只改真正需要改的地方。改动越小，将来重新生成越容易。

**怎么拿到官方模板做对比（这是唯一的权威来源）**

不用构建、不用联网，直接从 CLI 二进制里取：

```bash
cd /root/Tiez-Next
CLI=node_modules/@tauri-apps/cli-linux-x64-gnu/cli.linux-x64-gnu.node
python3 - "$CLI" <<'PY'
import sys
d = open(sys.argv[1], 'rb').read()
i = d.find(b'Unicode true')                       # 模板起点
j = d.find(b'Failed to setup handlebar template', i)   # 模板结束后的下一个二进制字符串
open('/tmp/upstream-installer.nsi','wb').write(d[i:j])
PY
diff -u /tmp/upstream-installer.nsi src-tauri/nsis/installer.nsi   # 应当只有上面那一处
```

结束时用 `Failed to setup handlebar template` 定位终点是**验证过的边界**：
该字符串紧跟模板末尾（`FunctionEnd`）出现，因此不会多截或少截。

**为什么不能直接改"构建产物里的那份"**
`<target>/release/nsis/x64/installer.nsi` 是**渲染后的成品**，所有 `{{...}}` 占位符都已被
替换成本机绝对路径和当时的版本号。把它当模板提交，等于把构造机上的一次性取值写死进仓库
（版本号、临时路径都会跟着固化）。所以仓库里放的是**未渲染的上游原文**，占位符原样保留。

自定义模板**同样会经过占位符渲染**（打包工具对官方与自定义模板走的是同一条
Handlebars 渲染管线），所以模板里的 `{{compression}}`、`{{product_name}}` 等必须保留。

**什么时候可以撤销**
如果上游把"默认直接覆盖"做成了配置项，或者这个项目不再需要 Windows 安装包，
就可以删掉自定义模板、恢复用官方的。

**这段"默认选中"怎么验证（已实测，不是推演）**

模板里那段逻辑处在一个超大的页面创建函数里，编译不过就整包编不出来，所以单独做了个探针：
`gen-reinstall-probe.py` 把**生产模板里的那段代码原样剪出来**（不是手抄），
拼进一个极小的安装程序，然后在 wine 里**真实运行**，直接读回两个单选按钮的实际勾选状态。

```bash
cd /root/Tiez-Next
python3 src-tauri/nsis/gen-reinstall-probe.py                 # 生成探针
makensis -V2 src-tauri/nsis/reinstall-default-selftest.nsi    # 编译
for m in 1 2 3 4 5 6; do                                      # 逐个用例真实运行
  wine src-tauri/nsis/reinstall-default-selftest.exe /MODE=$m
  cat ~/.wine/drive_c/tiez-probe/result.txt
done
```

实测结果（6 个用例全 PASS）：

| 用例 | 场景 | 预期默认选中 | 实测 |
|---|---|---|---|
| 1 | 升级，首次进入页面 | "请勿卸载" | ✅ |
| 2 | 降级，首次进入页面 | "请勿卸载" | ✅ |
| 3 | 同版本，首次进入页面 | "添加/重新安装"（保持上游） | ✅ |
| 4 | 升级，上次选过"安装前卸载" | "请勿卸载"（被覆盖） | ✅ |
| 5 | 同版本，上次选过"先卸载" | 保持用户选择 | ✅ |
| 6 | 升级，上次选过"请勿卸载" | 保持用户选择 | ✅ |

**反向对照（关键，别跳过）**：同一份探针换成**上游模板**再跑一遍，
用例 1、2、4 **必须变红**（实测确实变红），用例 3、5、6 保持绿色。
如果换成上游模板也全绿，说明这个探针根本没测到东西。

**验到的是"勾选"，不是"能不能点"——这点已经确认过**

用例 6 会保留用户上次选的"请勿卸载"。而模板在"不允许降级"的配置下
（`allowDowngrades=false`）会**禁用**这个按钮。两件事叠加会不会勾到一个禁用控件上？
实测结论：**会勾上，但没有问题**——`BM_SETCHECK` 对已禁用的按钮依然生效（读回仍是已勾选），
只是用户不能点它，所以不会因此产生任何越权操作。**本项目当前是 `allowDowngrades=true`**，
不存在这个组合；记在这里是为了将来有人关掉降级时知道已经核过，不必重新推演。

**两个已知坑**（重新做这类验证时会再踩）：
1. 探针**必须用图形模式跑**。NSIS 在静默模式（`/S`）下不会创建任何页面，
   而被测代码就在页面里——静默跑会"通过"，但其实一行都没执行。
2. 命令行 `/MODE=1` 经 `GetOptions "/MODE"` 取出来是字符串 `=1` 而不是 `1`。
   早期版本漏了这个等号，六个用例全部落进同一个分支、集体"通过"。
   现在未知模式一律判 FAIL，就是为了让这类挂具故障无法伪装成 PASS。

**另外：真实打包管线也跑过一次。** `tauri bundle` 用这份模板完成了渲染与编译，
产出的安装包与手工在沙箱里编译的**字节数完全一致**（4,833,217），
渲染后的模板里 `{{...}}` 占位符残留为 **0**——说明模板挂接方式是通的，
不只是"能单独编译"。

**当前没有覆盖到的部分**：WSL2 上没有 Windows 宿主，
`wine setup.exe /S` 退出码为 2、图形模式会挂起（改动前的版本在同一环境同样如此，
属于环境限制），因此**端到端"装一个旧版、再双击新版安装包、看默认勾选"没有实测**。
上面验证的是"那段判定逻辑在真实 Windows 控件上的行为"，不是完整安装流程。

## 二、刻意保留的旧名字（改了会坏数据）

> **这一组的共同点**：这些名字看起来是"改名没改干净"，其实**必须保留**。
> 删掉或改掉它们，会**损坏用户已有的数据**，而且不会有任何报错。

### M-02｜富文本内容里的标记前缀

**做了什么**
`src-tauri/src/services/clipboard/utils.rs` 里两个常量：

```rust
pub const RICH_IMAGE_FALLBACK_PREFIX: &str = "<!--TIEZ_RICH_IMAGE:";
pub const RICH_NAMED_FORMATS_PREFIX: &str = "<!--TIEZ_RICH_FORMATS:";
```

**为什么这么做**
这两个标记是**写进用户剪贴板记录正文里**的，早就存在用户的数据库中了。
改掉前缀，**旧记录就解析不出图片和格式了**——用户会发现历史记录里的图文变成一堆乱码。

**之后的人需要注意什么**
- 看到 "TIEZ" 字样不要"顺手改名"。判断标准是：**这个字符串是否已经写进了用户的数据里**。
- 如果确实需要新格式，做法是**新增一个标记并同时支持旧的**，而不是替换。

**什么时候可以撤销**
等有一天做一次数据迁移、把所有旧记录都重写一遍之后。在那之前不能动。

### M-03｜浏览器存储的键名

**做了什么**
前端 `localStorage` 里的 `tiez_theme`、`tiez_device_id` 等键。

**为什么这么做**
它们保存着用户的**主题选择、设备标识**等偏好。改键名等于**换了一个新键**，
旧键里的值还在但没人读它了——用户升级后发现"我的主题设置没了"。

**之后的人需要注意什么**
同 M-02 的判断标准：**这个键是否已经存在于用户机器上**。

**什么时候可以撤销**
当这些键里保存的信息不再被需要时（例如主题选择改由服务端或配置文件承载）。
撤销时的正确做法是**读一次旧键、把值迁到新位置、再删旧键**，而不是直接换名。

### M-04｜卸载脚本里对旧版本进程与注册表的清理

**做了什么**
`src-tauri/nsis/uninstall.nsh` 里除了清理本应用的进程与注册表，还清理了一批**旧名字**：
旧的进程名（`TieZ.exe`、`tiez-app.exe`）、旧的自启动项、旧的安装记录。

**为什么这么做**
从旧版本**覆盖安装**过来的用户，机器上还残留着旧版的进程、自启动项和安装记录。
不清理的话，会出现"程序删不干净""开机有两个自启动""控制面板里两条卸载项"这类问题。

**之后的人需要注意什么**
- 这些不是"没改干净"，是**给老用户准备的清理**。
- 将来如果确定已经没有任何老用户（比如过了足够长的兼容期），可以移除。
- **清理的时机很重要**：跨产品名升级时，新版安装器读不到旧版的安装记录，
  **不会运行旧版的卸载器**，所以这类清理必须放在**安装前**的钩子里，放"卸载时"是无效的。

**什么时候可以撤销**
当可以确定不会再有人从旧版本覆盖安装时（例如旧版本已停止分发足够长时间）。
判断方法：看旧版本的下载量是否已归零。在那之前移除，会让老用户的机器残留清理不掉。

### M-05｜数据库里针对历史数据的清理逻辑

**做了什么**
应用启动时会检查并清掉一些**指向旧版本服务**的配置残留。

**为什么这么做**
用户数据库里可能存在早先版本写入的、指向已废弃服务的配置项。留着它们会让应用
尝试连接一个不存在的服务。清理逻辑本身是**兼容历史**用的。

**之后的人需要注意什么**
看到"代码里出现了一个我们不认识的服务器域名，但它是被**清掉**的"——那是历史清理，不是遗留。

**什么时候可以撤销**
当可以确定所有用户的数据库里都不再有那条历史配置时。实践上这很难确定，
所以这类清理通常**长期保留**——它的成本极低（一条查询），而移除的风险是用户端出现怪问题。

## 三、安全与数据保护的强制约定

### M-06｜备份的路径护栏放在了内核里

**做了什么**
"不许把备份导出到数据目录内部"这条检查，从界面层的命令**下沉到了备份内核**
（`services/backup/export.rs` 的 `create_backup`）。

**为什么这么做**
这条检查原先只在**界面**的导出命令里。而通过 AI 接口（MCP）触发导出时**完全绕过了它**。
往数据目录里写备份会**截断正在使用的数据库**——写目标文件时若同名文件已存在会先被清空，
指向 `clipboard.db` 就是**不可逆的数据损毁**。

放在内核里，是因为那是**所有导出路径的唯一汇聚点**：谁调用都自动受保护。

**之后的人需要注意什么**
- **不要**把这条检查"还原"到调用方去做。加一个新的导出入口时，**不需要**再写一遍检查，
  内核已经管了；但**也不要**绕过 `create_backup` 去直接写文件。
- 同类原则：**保护性检查要放在唯一汇聚点**，而不是散落在每个调用方。
  散落式检查的失效模式是"新增调用方忘了加"，而且不会有测试失败。

**什么时候可以撤销**
如果将来备份功能重构，只要保证"存在一个所有导出都必经的入口，且入口处有这条检查"即可。

### M-07｜云同步整族排除 AI 接口配置

**做了什么**
`services/cloud_sync.rs` 的 `is_setting_sync_eligible` 里，用**前缀**排除所有 `mcp.` 开头的设置，
而不是逐个列举。

**为什么这么做**
这些设置里含有 AI 接口的**访问令牌**，以及"是否允许写入""是否允许局域网访问"这类
**安全姿态开关**。云同步会把远端的设置写回本地并持久化——于是**一个被篡改的远端快照
就能把这些危险配置种进这台机器**，等接口服务重启时生效，而用户从未在本地做过这个选择。

用前缀而不是逐键，是因为这族设置**会继续增加**：新增一个键时，逐键列举会**静默漏掉**它，
而漏掉一个键**不会有任何编译错误或测试失败**。

**之后的人需要注意什么**
- 给 AI 接口新增设置项时，**不需要**改这里——前缀已经覆盖了。
- 但**别改前缀**，也别把某条 `mcp.` 设置"加回"同步白名单，除非你确定它不含凭据与安全姿态。

**什么时候可以撤销**
只有当这一族设置里**不再包含任何凭据或安全姿态开关**时才可放宽。
在那之前，即使某个具体的键看起来"只是个端口号"，也不要单独放行——
逐键放行的失效模式就是本文档反复强调的那个：新增键时静默漏掉。

### M-08｜备份导出的路径规范化必须处理"文件还不存在"

**做了什么**
`canonicalize_for_guard`：因为路径规范化的标准做法要求路径**已经存在**，
而"用户挑了一个还不存在的新文件名"是**常态**，所以这里规范化**父目录**再把文件名拼回去。

**为什么这么做**
路径规范化的标准做法要求路径**已经存在**，而"用户挑了一个还不存在的新文件名"
是**常态**（用户总是指定一个新文件）。若照搬标准做法，护栏在最常见的场景下根本跑不到。

**之后的人需要注意什么**
改动这段时要保持"路径不存在也能判定"的能力，否则护栏会在最常见的场景下**静默失效**
（因为通常会写成"取不到规范化结果就放行"）。

**什么时候可以撤销**
这段是通用的路径处理技巧，只要还有"校验一个尚不存在的输出路径"的需求，就该保留。

## 四、测试与断言的特殊处理

### M-09｜有一条测试测的是"旧行为是错的"

**做了什么**
`src-tauri/src/app/commands/system_cmd.rs` 里的
`customized_setting_still_counts_as_pristine`，以及它旁边那条
`settings_alone_do_not_override_real_user_data`。

**为什么这么做**
这里原先有一条测试 `customized_setting_makes_target_non_pristine`，
断言"用户改过设置就不能算空库"。**那个断言保护的是一个真实缺陷**：

判断"这份数据目录能不能被迁移接管"时，原先要求设置与全新安装**逐键完全相等**。
但应用自己会写设置——最平凡的是**窗口尺寸**（拖动一下窗口就会写）。
于是用户只要调整过窗口大小，迁移就**永远**被拒绝，界面却说"已经有你自己的记录"，
而用户看到的记录数是 0。

**之后的人需要注意什么**
- 这两条测试**互为反向**，一起看才有意义：一条说"只改设置仍可接管"，
  另一条说"有真实数据就不行"。**只留一条会把判据改歪**。
- 这个案例的通用教训：**一条测试可以保护一个缺陷**。测试全绿不等于功能正确。
  判断一条测试是否有价值的方法是**把它对着改动前的实现跑一遍**——如果照样通过，
  它就没在保护任何东西（参见 M-10）。

**什么时候可以撤销**
这两条测试长期保留。它们是"判据为什么是这样"的**唯一书面依据**——
如果哪天有人觉得"改设置后就不该算空库"，会先在这里看到理由。

### M-10｜有一组测试专门断言"菜单真的打开了"

**做了什么**
标签分组右键菜单的测试（`TagManager.tagMenu.test.tsx`）里，每条"某某操作会关闭菜单"
的断言前面，都先加了一句"菜单确实打开了"。

**为什么这么做**
不加那句时，这些断言是**恒真**的：如果菜单**根本打不开**，
"关闭后菜单不存在"自然成立。也就是说，**对着一个完全没有菜单的实现，测试照样全绿**。

**之后的人需要注意什么**
- 写"某某东西不存在了"这类断言时，**必须先证明它存在过**。
- 这类陷阱的通用形式：**空集合上的一切断言都成立**。
  对空列表断言"没有某个子元素"、对未渲染的组件断言"没有某个按钮"，都属于此列。
- 检查方法同样是**反向对照**：把实现退回改动前，看测试是否变红。

**什么时候可以撤销**
这些"存在性前置"不能删——删掉它们，那批断言就退回恒真状态。
若将来菜单组件的实现方式大变（例如换成原生菜单），需要**重新做一次反向对照**，
确认新写法下的断言依然能抓到"菜单没打开"。

## 五、被移除功能留下的痕迹

### M-11｜在线主题商店被移除，但"未知主题"要有兜底

**做了什么**
整个在线主题商店（浏览、上传、评分、账号）连同入口一起删除。
同时，主题 id 的归一化函数改成：**遇到不认识的 id 就回退到默认主题**。

**为什么这么做**
如果用户此前选用过商店里的主题，它的主题 id 就存在用户的设置里。
商店删除后，这个 id **不再有任何样式对应**——不做兜底，界面会处于一个"主题 id 存在但无样式"的状态。
回退到默认主题是**能在用户不察觉的情况下恢复可用**的做法。

**之后的人需要注意什么**
- 移除一个"用户可能已经选了某个值"的功能时，**要检查那个值还在不在用户设置里**，并给兜底。
- 兜底**不要写回**用户的设置（保留原值），这样如果将来恢复了该功能还能用；
  这也让这个改动是**可逆**的。

**什么时候可以撤销**
如果将来重新提供主题商店（或等价的主题分发渠道），且那个主题 id 能重新被解析，
这个兜底就可以保留不动——它只在"认不出的 id"上生效，不会干扰正常主题。

### M-12｜不再请求上游服务器，但数据库里仍有清理逻辑

**做了什么**
移除了启动时和定时向原项目服务器发送的请求（该请求还带有机器标识）。
前端那半边已彻底删除；后端那半边原本藏在一个环境变量后面，也一并删除。

**为什么这么做**
用户已经明确不要向原项目（这个项目的上游）的服务器发送任何数据。
那个请求还会带上机器标识，属于不必要的数据外发。

**之后的人需要注意什么**
- 代码里若出现**原项目的域名**，先判断它是"**要清理的历史残留**"还是"**要请求的目标**"。
  前者是正当的，后者不该存在。
- 具体来说，数据库初始化里有一条把某个指向原项目的配置项**置空**的逻辑，那是清理，保留。

**什么时候可以撤销**
- 请求：不再需要撤销，这是长期决定。
- 清理逻辑：同 M-05，等所有用户的数据库里都不再有那条配置。

## 六、尚未偿还的设计债

> 这些是**已知的、暂时不修的问题**。写在这里是为了让接手的人知道"这不是没发现，
> 是权衡后决定先不做"，以及**在什么条件下应该回来处理它**。

### M-13｜"便携模式"是一个编译期开关，却与运行期的判定不同步

**做了什么**
保留了一个编译期特性开关，它控制"敏感设置不加密"和"搜索走明文"。
同时程序在**运行期**另有机制判断"是不是便携模式"。两者**并行存在，互不同步**。

**为什么这么做**
这是历史遗留：编译期开关与运行期判定是不同时期引入的，各自为了解决当时的问题，
没有人把它们合并。当前发布构建**不启用**这个特性开关，因此加密是正常生效的。

**为什么暂时不修**
改动它会牵动加密路径——而加密路径一旦改错，后果是用户数据被明文写入或读不出来。
以"语义不够整齐"为由去动一条数据安全路径，风险远大于收益。

**之后的人需要注意什么**
- 看到这个编译期开关时，**不要以为它在当前构建里生效**。发布构建未启用它。
- 它的存在会让"便携模式到底加不加密"这个问题有两个互相矛盾的答案，
  这本身就是需要处理的信号——但要在**有充分测试覆盖**的前提下处理，不要顺手改。

**现状**
代码里有一个编译期的特性开关 `portable`，它控制"敏感设置不加密"和"搜索走明文"。
同时，程序在**运行期**会根据"程序目录下是否存在 `data` 文件夹"来判断是不是便携模式。

**问题**
两者**互不同步**：编译期开关与运行期判定是两套独立的机制。
结果是"便携版用户实际**有**加密，而这个开关的意图是便携版不加密"——**语义对不上**。

**为什么暂时不修**
它**不影响当前的发布构建**：发布时并未启用该特性开关，加密是正常生效的。
而改动它会牵动加密路径，风险远大于收益。

**什么时候该回来处理**
当确定不再需要"便携模式"这个概念时（例如数据已完全移出程序目录、不再有便携形态的部署），
把编译期特性与运行期判定**合并成一套**，或者干脆删掉。

### M-14｜两处"复制后删源"的数据搬迁没有中途回滚

**现状**
"更改数据存储位置"功能在搬迁时是**先复制到新位置、成功后再删旧位置**。
如果中途失败，**已经搬过去的部分不会回滚**，会留下"一半在这边一半在那边"的状态。

相比之下，**迁移中心**那条路径严格得多：源目录全程只读、先写暂存、校验通过后才交付。

**为什么这么做**
两条路径是不同时期写的，目标不同：一条是"改个存储位置"的便利功能，
另一条后来被要求做到"即使失败也绝不丢数据"。安全等级因此不一致。

**之后的人需要注意什么**
改动前者时，**不要以为它和后者的安全性相同**。

**之后的人需要注意什么**
- 两条路径**安全等级不同**，改动时不要以为它们等价。
- 理想做法是把前者**统一到后者的契约**上（源只读、暂存校验、失败可完整回退）。

### M-15｜未定义的 CSS 变量是一类沉默缺陷

**做了什么**
项目里有一批 `var(--x)` 写法，而 `--x` **从未被定义过**。实测扫描（全部 `.css/.ts/.tsx` 的
`var()` 使用点 vs 全部 `--x:` 声明做集合差）：使用 251 个、定义 239 个、**缺失 38 个**。

**为什么要注意**
浏览器不会报错、构建不会失败、类型检查不会发现 —— **`var()` 取不到值时整条 CSS 声明被静默丢弃**。
界面"看起来正常"，只是该有的边框/背景/阴影没了。实测最明显的一处：某数字输入框
`border: 1px solid var(--border-color)` 因为变量缺失而**完全没有边框**，而代码看上去完全正常。

成因通常是两种：**从别处照抄写法**；或**以为通用命名存在** ——
而本项目真实使用的是一套**语义化命名**（`--button-radius` / `--card-radius` /
`--input-radius` / `--panel-radius`；背景族是 `--bg-body` / `--bg-content` / `--bg-element`），
所以 `--radius-sm` / `--bg-main` / `--bg-secondary` 这类通用名**从未被实现**。

**之后的人需要注意什么**
- 新增或复制组件样式时，**确认变量真的存在**，不要凭命名习惯假设。
- 修复时**优先映射到既有语义化变量**，不要为了"让这处生效"而新引入一套通用命名 ——
  那会让项目里同时存在两种命名族。
- 已加了一条可复跑的检查（见该批次的实现），让"用了未定义的变量"将来能被自动发现。
  **这类缺陷能长期存在的根本原因就是没有任何机制会报警。**

**什么时候可以撤销**
检查机制长期保留。变量映射本身随组件演进，但**"不要引入第二套命名"这条约束不变**。

#### 怎么判断"该修"还是"该登记豁免"（实测判据）

不是所有"变量缺失"都要改 —— **要看它缺失时用户还能不能看见**：

| 写法 | 缺失时 | 处置 |
|---|---|---|
| `var(--x)`（无兜底） | **整条声明被丢弃** | **必须修** |
| `rgba(var(--x), a)` | 同上（变量在颜色函数里，兜底救不回来） | **必须修** |
| `var(--x, <项目真实令牌>)` | 走兜底，样式**照常生效** | **登记豁免**（改它等于改观感） |

实测两例恰好构成对照：

- `compact-mode.css` 里一处写 `var(--border-color, rgba(0,0,0,0.1))` —— 兜底是**黑色**，
  **深色主题下那条边框等于不可见** ⇒ **必须修**（已改为项目真实令牌 `--card-border`）
- 另 12 处写 `var(--border-color, rgba(128,128,128,0.25))` —— 兜底是**中性灰**，
  明暗主题下都可见 ⇒ **登记豁免**（改动会挪动既有像素，属于改设计而非修缺陷）

**判据**：兜底值在**所有主题下是否都产生预期效果**。是 → 豁免；否 → 修。

**另一个真实陷阱**：把 `1px solid var(--x, <颜色>)` 里的变量换成项目里**自带 `1px solid`** 的
组件级令牌（如 `--card-border`），会变成 `1px solid 1px solid ...` 而**整条失效** ——
这恰恰是要避免的那类静默丢弃。替换前先看**调用方在括号外拼了什么**。

### M-16｜备份压缩要按「内容是否还可压」分流

**做了什么**
备份导出原先用同一个压缩方法处理所有内容：数据库用**不压缩**（`Stored`），
图片目录用 **deflate**。实测这个组合是**负收益** —— 163 MiB 数据上**整包比原数据还大 1.4%**。

**为什么这么做（方向曾经是反的）**
关键在于**分清"内容本身可不可压"**，而不是"它是不是数据库文件"：

| 内容 | 性质 | 实测压缩率 |
|---|---|---|
| 数据库文件 | SQLite，里面装的是**文本** | **0.23** ← 唯一真正值得压的 |
| 附件目录 | 图片，**落盘前已是 PNG/JPEG** | 0.98（烧 1119 ms 只换 1.18 MiB） |
| 表情目录 | 两万多个 ~3 KB 小 PNG | **1.33（膨胀 33%）** |
| 数据库写前日志 | 二进制 | 低级别下涨 5.5% |

两个反直觉事实：**①「数据库文件」不等于「已压缩」**——决定因素是里面装了什么；
**②小文件压缩会净膨胀** —— ZIP 每条目固定开销实测约 134 字节，对中位数 393 字节的小文件
就是 34%，这是**结构性问题，换任何算法都解决不了**。

**之后的人需要注意什么**
- 现在是：**只有数据库压缩，其余一律只打包（`Stored`）**。改这个策略前先看实测数据。
- **不要为了"更安全/更小"而换成 zstd**：实测 zstd 各档在压缩率上能略超 deflate，
  但 `CompressionMethod::Zstd` 是 feature-gated 的，**旧版本 reader 遇到不认识的压缩方法编号
  会整个包读取失败**（而非跳过该条目）。收益不到 1%，不值得破坏向下兼容。
- **不要为了"更快"而多线程压缩**：实测单线程在多个 CPU 争抢模型下**零丢帧**，
  而 ≥5 并行才把 p95 从约 16 ms 抬到 20–23 ms。
- **不要加 CPU 优先级下调 / 分块让渡 / 限速**：实测优先级下调无效
  （争抢源于"线程数 > 空闲核数"，降优先级只改变"谁等谁"）；压缩是 IO 绑定，
  单线程本身就在大量让出 CPU。

**什么时候可以撤销**
若将来 `clipboard.db` 普遍大到"单核压缩突发"成为用户可感知的问题
（实测 90 MiB 库时 deflate-6 有一次 1.48 秒的单核连续占用，zstd-1 只需 0.225 秒），
再重新评估这个取舍。当前真实量级是 18 MiB，突发 277 ms。

## 如何新增条目

**什么时候该加一条：**

- 你做的一个决定，会让**之后的人**在做某件事时多一层顾虑或额外步骤；
- 你为了某个目的**刻意保留**了一段看起来过时/错误的东西；
- 你引入了**与上游分叉**的文件；
- 你**移除**了一个用户可能已经依赖的东西；
- 你发现了一个**暂时决定不修**的问题。

**每条必须包含四部分**（缺了就不算写完整）：

1. **做了什么** —— 事实，可核对（带上文件路径）
2. **为什么这么做** —— 当时的真实理由。如果是为了修一个缺陷，**把缺陷描述清楚**：
   用户会遇到什么现象、后果多严重
3. **之后的人需要注意什么** —— 这是最有价值的部分。写"看到 X 不要改 Y"、
   "加新东西时不需要/必须做什么"
4. **什么时候可以撤销** —— 明确条件。**没有撤销条件的条目，会永远没人敢动它**

**写作要求：**

- **自包含**：不假设读者读过提交记录、需求文档或任何人的笔记。
  可以引用文件路径，但不要引用"上次讨论的结论"。
- **讲现象，不只讲结论**：写"用户拖动窗口后迁移就永远失败"比写"判据过严"有用得多。
- **不写具体人名、日期当作理由**："因为某人要求"不是理由；"因为不这样会损坏用户数据"才是。
- **保持这份文档本身可独立阅读**：它是长期资产，不要让它变成一张只有当时的人看得懂的便条。

**编号**：`M-NN`，只增不改。撤销的条目不删除，改为标注「已撤销（原因 + 何时）」，
保留编号，避免别处的引用失效。
