### 1.2 MCP 当前默认值（实测）

| 项 | 当前 | 目标 |
|---|---|---|
| 启用 | 默认关闭 | **默认开启** |

### 1.3 分栏比例闪烁根因（已定位）

`TagManager.tsx:286`：
```ts
const sidebarSizeRef = useRef<TagManagerSidebarSize>({ ...DEFAULT_TAG_MANAGER_SIZE });
```
初始值是**默认比例**，要等 `invoke('get_settings')` 异步返回（`:363-366`）才改成记忆值。因此必然先渲染默认比例再跳变。

**这是"卡一下"的确切原因**，不是渲染性能问题。

### 1.4 备注图标

`ClipboardItem.tsx:33` 引入 `StickyNote`，用在 `:1607`（编辑按钮）与 `:2078`（备注显示）。需求是把**备注前面的图标**改为 ✨。

### 1.5 迁移中心识别范围

`migration_identifier.rs:52`：
```rust
pub const LEGACY_IDENTIFIERS: &[&str] = &["com.tiez.app", "com.tiez"];
```
仅识别 TieZ 的两个历史标识符。**不包含 `com.tieznext` 自身**——这正是第六条要求扩展的点。

## 二、批次划分

### B1｜应用标识统一（需求①）

- 清理上述 5 处 `TieZ` 字样（`migration.rs` 的历史日志除外，见下）
- **保留**卸载器的旧进程/注册表清理（`TieZ.exe`、`tiez-app.exe`），因为覆盖安装的老用户仍需清理干净——但**日志文字改为 Tiez-Next**
- 确认并处理托盘图标：区分"图标图形"与"提示文字"
- **验证**：交叉编译后检查安装器产物内的字符串

**关于 `migration.rs`**：其中的「贴汁 → TieZ」是**历史事实记录**（描述过去发生过的迁移），不是当前标识。改为 Tiez-Next 会让历史描述失真。**保留原样**并在注释中说明。

### B2｜MCP 默认可用化（需求②）

- `DEFAULT_PORT`: 39217 → **23123**
- 启用默认值：false → **true**
- 写权限默认值：false → **true**
- 令牌：默认**不校验**（保留令牌能力，改为可选）
- 绑定地址：`Ipv4Addr::LOCALHOST` → **可配置**，默认仍为本机
- **集成**：新增 `mcp.allow_lan` 设置项；绑定地址随其变化
- **验证**：单元测试覆盖"默认值即目标值"；实测本机与局域网可达性差异

**安全说明**：本次是用户对安全默认值的**明确改判**（v0.4 是只读+令牌）。实现时仍需保留这些能力（可关闭），并在界面上如实说明当前暴露面。

### B3｜MCP 界面美化（需求③）

- 对照相邻设置项（如备份、数据目录）的视觉语言重做 `McpSettingsGroup.tsx`
- 保留功能，统一间距、字号、按钮样式、说明文字层级
- **验证**：组件级截图对比（沿用既有方法）

### B4｜分栏比例消除闪烁（需求④）

- **方案**：在打开标签管理**之前**预取设置（父层或应用启动时），使首帧即拿到记忆值
- 备选：把比例注入 CSS 变量，首帧由样式表决定
- 保留现有 `sidebarSizeRef` + 防抖持久化逻辑不变
- **验证**：现有 29 个测试保持通过；新增"首帧即记忆值"的回归测试

### B5｜备注图标改为 ✨（需求⑤）

- `ClipboardItem.tsx`：备注前置图标 `StickyNote` → `Sparkles`
- 三语文案如需同步调整则一并处理
- **验证**：组件级截图

### B6｜迁移中心支持自身迁移（需求⑥）

- `LEGACY_IDENTIFIERS` 的语义从"旧版标识符"扩展为**"可迁移来源"**
- 支持 `com.tieznext`（自身，含后续版本）作为合法迁移来源
- 界面文案区分两类来源：**旧版 TieZ** 与 **Tiez-Next 历史版本**
- 安全契约不变：只读源、失败不动原数据、可反复执行
- **验证**：新增测试覆盖"从 Tiez-Next 目录迁移"

**依赖**：需先确认 Q1（用户旧版数据目录的具体路径）。

### B8｜标签条目的移动与复制（需求第九条）

**新增能力**，当前完全不存在。

侦察结论：
- `tag_repo` 已有 `update_entry_tags(id, tags)`（`tag_repo.rs:294`），**移动/复制可建立在其之上**
- Tauri 命令层**没有**任何 move/copy 相关命令（`main.rs` 标签命令仅 get/rename/delete/create/update_tags/colors）
- 前端**没有**右键菜单基础设施（`ClipboardItem.tsx` 与 `EmojiPanel.tsx` 有 `onContextMenu` 但只是阻止冒泡）

**实现范围**：
1. **移动**：把条目从标签 A 移到标签 B（A 移除、B 加入）
2. **复制**：条目同时属于 A 与 B（保留 A、加入 B）
3. **UI**：条目上的入口（右键菜单或按钮）
4. **MCP**：对应的工具

**关键设计问题（需在实现前定）**：条目与标签是多对多还是单一归属？
- 若多对多 → "移动"语义为"从 A 的集合中移除、加入 B"
- 若是唯一归属 → "移动"会替换所有标签
必须在实现前查清 `entry_tags` 表结构与 `update_entry_tags` 的实际语义，**不可猜测**。

### B9｜标签组操作改为右键菜单（需求第十条）

- `TagManager.tsx:846`（重命名）、`:857`（删除）两个直接显示的 `<span>`
- 改为右键菜单触发，消除对标签选择的视觉遮挡
- 需新建右键菜单组件（项目内无现成基础设施）
- 保留现有功能与二次确认（删除仍需确认）
- **验证**：组件级截图对比改动前后

### B10｜MCP 能力扩展至与 UI 对等（需求第八条 + 第九条的原则）

**这是架构原则，优先级高于单点功能**：「人能操作的，MCP 也要支持」。

**执行方式**：
1. **先盘点**：列出 UI 上所有条目/标签操作
2. **比对**：逐项检查 MCP 是否已支持
3. **补齐缺口**：为缺失项加 MCP 工具
4. **验证对等性**：写一个测试断言"UI 命令集与 MCP 工具集覆盖相同的操作面"

**注意**：用户特别举例了"删除标签组"——MCP 现有 17 个工具中**已有** `delete_tag`，需核实其语义是否与 UI 的删除一致（v0.4 修过"删分组不删条目"，MCP 必须走同一路径）。

### B7｜独立复核（ULW 要求）

- 全部批次完成后派**独立复核子代理**，以原始需求为唯一依据
- 复核未通过则修复并重验

## 四、风险

| 风险 | 说明 | 处置 |
|---|---|---|
| 安装器文字改动无法本地验证 | NSIS 产物在 Linux 交叉编译，安装界面需 Windows 实机 | 用字符串扫描验证产物内含正确文字，实机留给用户 |
| MCP 默认免鉴权 + 局域网 | 暴露面显著扩大 | 严格默认本机；界面显著提示；保留开关 |
| 托盘图标改动 | 需先确认改的是图形还是文字 | 先问 Q2 之外单独确认 |
| 分栏比例预取 | 可能牵动设置加载时机 | 保持既有测试全绿为准绳 |
| **MCP 与 UI 能力不对等** | 用户明确要求"人能操作的 MCP 也要有" | B10 以清单方式逐项比对，不靠印象 |
| 条目-标签关系语义不明 | 移动/复制的行为取决于多对多还是唯一归属 | B8 实现前必须先读表结构确认 |
| 右键菜单新组件 | 项目内无现成基础设施 | 参考 `ClipboardItem.tsx` 既有 portal 用法 |
